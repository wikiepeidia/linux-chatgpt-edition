# Technology Stack

**Project:** 300K Linux
**Researched:** 2026-08-25
**Overall confidence:** MEDIUM

## Decision

Build 300K Linux as a **custom Alpine Linux 3.24.1 x86_64 diskless ISO**, generated from Alpine's `3.24-stable` `aports/scripts/mkimage.sh` inside a pinned Linux/amd64 Docker image. Start from the `profile_virt` design, replace its runtime package set with the project's own minimal list, and retain Alpine's hybrid **ISOLINUX BIOS + GRUB x86_64 EFI** output.

Use **Xorg + Openbox + Tcl/Tk + xterm** for the running experience. The ChatGPT-inspired shell should be a full-screen `wish` script, not a browser. A button launches a themed `xterm` running the real local BusyBox `ash` shell. This avoids Chromium/WebKit, Python, Node, a display manager, and a full desktop environment.

This is the best overnight trade: not the absolute smallest theoretical image, but the smallest option found with a current stable release, maintained x86_64 packages, an official custom-ISO builder, and a source-confirmed hybrid BIOS/UEFI path.

## Base Comparison

| Candidate | Current official evidence | Build/boot fit | Decision |
|---|---|---|---|
| **Alpine Linux 3.24.1** | Released 2026-06-13. The official x86_64 directory reports the 3.24.1 `virt` ISO as **66M**, `minirootfs` as **4M**, and `standard` ISO as **352M**. The supported `v3.24` branch runs through 2028-06-01. | `mkimage.sh` has profiles, APK dependency resolution, apkovl support, ISOLINUX, GRUB EFI, `mtools`, and `xorrisofs` hybrid output. | **Use it.** |
| **Tiny Core Pure64 17.0** | Official 2026-02-10 artifacts are exceptionally small: `CorePure64-17.0.iso` is **25,853,952 bytes** and `TinyCorePure64-17.0.iso` is **42,991,616 bytes**. | Official remaster documentation publishes a manual cpio/gzip/mkisofs flow and a BIOS ISOLINUX recipe. The current Core book discusses UEFI installations, but no equally clear current official hybrid BIOS+UEFI ISO remaster path was found. Its extension model would also make a polished custom UI more bespoke. | Reject for v1 schedule risk; revisit only if Alpine cannot approach the size target. |
| **SliTaz Cooking / 5.1 in development** | Official downloads advertise a 55 MB Cooking desktop and a separate native x86_64 Cooking base image; the project says 5.1 is still being developed. July 2026 notes show active x86_64 and GRUB2-EFI work. | Impressively small and active, but the native x86_64 line is still a development target rather than the conservative stable base for a one-night release. | Reject for v1 stability/tooling risk. |
| **Debian live-build / Archiso / Fedora live tooling** | Mature, documented ecosystems. | Their general-purpose live-image defaults and dependency footprints work against the near-100-MB target; trimming them would consume the night without improving the parody UI. | Reject for v1 size and iteration speed. |
| **Buildroot** | Purpose-built minimal appliance images are possible. | It shifts the job into source builds, kernel configuration, device integration, and package recipes. That is excellent for a later appliance edition, not the fastest route to a polished live desktop tonight. | Defer. |

## Recommended Stack

### Image and Boot Layer

| Technology | Pin | Purpose | Why |
|---|---|---|---|
| Alpine Linux | `3.24.1`, repositories under `/alpine/v3.24` | Runtime base and package source | Current stable x86_64 release with a small official `virt` baseline. |
| Alpine Docker Official Image | `alpine:3.24.1@sha256:28bd5fe8b56d1bd048e5babf5b10710ebe0bae67db86916198a6eec434943f8b` | Linux build environment on Windows | Docker Hub currently maps 3.24.1 to this multi-platform index digest. Use `--platform linux/amd64`. |
| Alpine aports | branch `3.24-stable`; record the resolved commit in `build-lock.json` | ISO profile and image generator | Keeps image logic aligned with the v3.24 package repositories. Do not build from moving `master`/`edge`. |
| `linux-virt` | exact APK version captured during the first successful build | VM-focused kernel/modloop | Alpine's official `profile_virt` selects the slimmed virtual kernel. |
| ISOLINUX/Syslinux | v3.24 package lock | Legacy BIOS El Torito boot | Generated by Alpine's image scripts for x86/x86_64 ISO output. |
| GRUB EFI | `grub-efi 2.14-r0` in v3.24 at research time | `EFI/BOOT/BOOTX64.EFI` path | Current aports source builds `bootx64.efi` and an EFI FAT image. |
| `xorriso` + `mtools` | v3.24 package lock | Hybrid ISO assembly | Aports uses `xorrisofs` with an isohybrid MBR, alternate EFI El Torito image, and GPT hybrid marker. |
| Alpine apkovl | project script, versioned in repo | Boot-time configuration and project files | Natural Alpine diskless mechanism for users, OpenRC services, X startup, UI scripts, branding, and `/etc/apk/world`. |

### Graphical Runtime

| Package | Version/pin | Purpose | Notes |
|---|---|---|---|
| `xorg-server` | v3.24 package lock; package version observed as `21.1.24-r0` | X11 display server | Use QEMU's `virtio-vga`; include the normal modesetting stack for reliability before attempting size cuts. |
| `xinit`, `eudev`, `xf86-input-libinput`, `mesa-dri-gallium` | v3.24 package lock | Session startup, devices, input, rendering | First reliable package set. Remove or replace only after BIOS and UEFI boots are green. |
| `openbox` | `3.6.1-r8` | Minimal window manager | Small, packaged, and explicitly documented by Alpine. No panel or desktop shell is needed. |
| `tcl` + `tk` | Tcl `8.6.17-r1`; lock Tk from v3.24 | Full-screen parody UI | Scriptable native widgets and canvas drawing with no browser or Python runtime. |
| `xterm` | v3.24 package lock | Real “ChatGPT Terminal” | Launch `/bin/ash -l`; theme via X resources/arguments. |
| `font-terminus` | v3.24 package lock | Legible compact UI/terminal font | Alpine's own Openbox guide recommends it with Openbox and xterm. |
| BusyBox/OpenRC | supplied by `alpine-base` | Shell, core utilities, init | Gives a genuinely usable offline terminal without GNU userland bulk. |

Initial runtime APK set:

```text
alpine-base busybox eudev
xorg-server xinit xf86-input-libinput mesa-dri-gallium
openbox xterm font-terminus
tcl tk
```

Do not add Chromium, Firefox, WebKitGTK, Electron, Node.js, Python, XFCE, LXQt, a display manager, NetworkManager, or office/media suites to v1. The local UI does not need an HTML renderer, and each of those choices would spend size and boot-debug budget on machinery unrelated to the core joke.

## Exact Builder Toolchain

Install these inside the pinned Alpine builder image:

```sh
apk add --no-cache \
  abuild alpine-conf git \
  grub grub-efi mtools \
  squashfs-tools syslinux xorriso
```

Alpine's official custom-ISO documentation names `abuild`, `alpine-conf`, `syslinux`, `xorriso`, `squashfs-tools`, `grub`, and `mtools` for EFI. `git` is added only to pin and obtain aports.

The repository should own these build inputs:

```text
build/
  Dockerfile
  build.ps1
  build.sh
  mkimg.300k.sh
  genapkovl-300k.sh
overlay/
  etc/
  home/chatgpt/
  usr/local/bin/
dist/                  # generated, ignored except checksums/releases
```

Copy `mkimg.300k.sh` and `genapkovl-300k.sh` into `/opt/aports/scripts/` before invoking `mkimage.sh`. The profile should call `profile_virt`, then override `title`, `profile_abbrev`, `hostname`, `apks`, `apkovl`, boot timeout, and project-specific kernel command line. Keep the inherited `grub_mod` value: in current aports it is what activates the EFI section. Keep both main and community v3.24 repositories because Openbox/X packages span them. Have the wrapper normalize the generated name to `300k-linux-x86_64.iso` only after a successful build.

Representative stable invocation inside the container:

```sh
export SOURCE_DATE_EPOCH=1787688000
sh /opt/aports/scripts/mkimage.sh \
  --tag 3.24.1 \
  --arch x86_64 \
  --profile 300k \
  --workdir /work \
  --outdir /out \
  --repository https://dl-cdn.alpinelinux.org/alpine/v3.24/main \
  --repository https://dl-cdn.alpinelinux.org/alpine/v3.24/community
```

The epoch above is a deliberately fixed project build value; record it in `build-lock.json` instead of replacing it with the wall clock.

Use a project-local APK signing key generated once and kept out of Git, or explicitly document a public throwaway build key if bit-for-bit public reproduction becomes a requirement. Do not generate a new signing key on every ordinary rebuild.

## Windows and Docker Feasibility

**Verdict: feasible, with one immediate host prerequisite.** The installed Docker client is 29.6.0, but the Docker daemon was not running during research (`docker_engine` named pipe absent). Phase 1 must start Docker Desktop in Linux-container mode and prove `docker run --rm --platform linux/amd64 alpine:3.24.1 uname -m` returns `x86_64` before UI work begins.

No WSL command is needed by this build. Docker Desktop still needs a functioning Linux-container backend (Hyper-V or its configured alternative). If Docker Desktop cannot provide one, use a small Alpine build VM under the already installed QEMU; keep the same aports profile rather than changing distributions.

Build inside the container filesystem or a Docker named volume and bind-mount only `/out` to Windows. This avoids Windows executable-bit, symlink, ownership, and CRLF problems in aports. Copy project scripts into the builder image with explicit modes (`COPY --chmod=0755`) and enforce LF in `.gitattributes`.

PowerShell orchestration shape:

```powershell
docker build --platform linux/amd64 -t 300k-iso-builder:3.24.1 -f build/Dockerfile .

New-Item -ItemType Directory -Force .\dist | Out-Null
$distPath = (Resolve-Path .\dist).Path

docker run --rm --platform linux/amd64 `
  --mount "type=bind,source=$distPath,target=/out" `
  --mount "type=volume,source=300k-iso-work,target=/work" `
  300k-iso-builder:3.24.1

Get-FileHash .\dist\300k-linux-*.iso -Algorithm SHA256
```

The first build requires network access to pull the builder, clone/fetch the pinned aports ref, and download APKs. The produced ISO must not require network access.

## BIOS and UEFI

**Both are feasible for v1, without Secure Boot.** Current aports source does all of the following for x86_64 ISO output:

1. adds ISOLINUX and an isohybrid MBR for legacy BIOS;
2. builds `bootx64.efi` with GRUB;
3. creates a FAT EFI image with `mformat`/`mcopy`;
4. adds it as the alternate El Torito boot image;
5. emits the ISO with `-isohybrid-gpt-basdat`, making raw USB writing practical.

Do not sign or claim Secure Boot support in v1. Test ordinary UEFI with Secure Boot disabled.

The local QEMU installation was verified as **11.1.0** at `D:\VM\qemu`. It contains `share\edk2-x86_64-code.fd` and `share\edk2-i386-vars.fd`.

BIOS smoke boot (default SeaBIOS):

```powershell
$qemu = 'D:\VM\qemu\qemu-system-x86_64.exe'
$iso = (Resolve-Path '.\dist\300k-linux-x86_64.iso').Path

& $qemu -machine q35 -m 512M -smp 2 `
  -boot order=d -cdrom $iso `
  -device virtio-vga -device qemu-xhci -device usb-tablet `
  -nic none
```

UEFI smoke boot (copy the writable variables template first):

```powershell
$qemu = 'D:\VM\qemu\qemu-system-x86_64.exe'
$iso = (Resolve-Path '.\dist\300k-linux-x86_64.iso').Path
$code = 'D:\VM\qemu\share\edk2-x86_64-code.fd'

Copy-Item -Force 'D:\VM\qemu\share\edk2-i386-vars.fd' '.\build\edk2-vars.fd'
$vars = (Resolve-Path '.\build\edk2-vars.fd').Path

& $qemu -machine q35 -m 512M -smp 2 `
  -drive "if=pflash,format=raw,readonly=on,file=$code" `
  -drive "if=pflash,format=raw,file=$vars" `
  -boot order=d -cdrom $iso `
  -device virtio-vga -device qemu-xhci -device usb-tablet `
  -nic none
```

Never attach the shipped vars template writable; always test with a copied file. `-nic none` proves the experience does not depend on a network.

## Size Contract

The only defensible current baseline is Alpine's official **66M** `virt` ISO listing. A hard 100 MB result is **not yet verified**. Relative to that published artifact, a literal 100 MB ceiling leaves roughly 34 MB for all compressed Xorg, fonts, Tk, terminal, UI assets, and changed package composition. The custom profile may also remove packages from `profile_virt`, so it is not a simple additive calculation.

Roadmap gates should therefore be:

1. build and boot the smallest reliable graphical profile;
2. record total ISO bytes and the compressed contribution of each APK group;
3. remove network/server packages, unused firmware, docs/locales, and oversized assets one group at a time;
4. keep the last BIOS+UEFI-green image even if it exceeds 100 MB.

Do not publish an estimated final size before the first measured build.

## Reproducibility Contract

For a repeatable build, record and verify:

- Docker image index digest and resolved linux/amd64 manifest;
- exact aports commit from `3.24-stable`;
- repository URLs and the resolved APK names/versions/checksums;
- project APK signing-key fingerprint;
- fixed `SOURCE_DATE_EPOCH`;
- ISO SHA-256, byte size, and `xorriso -indev ... -report_el_torito as_mkisofs` output;
- BIOS and UEFI QEMU command lines and smoke-test results.

Pinning only `v3.24` is enough for a repeatable workflow, but not for a future bit-identical ISO because Alpine repositories receive package updates. Preserve the fetched APK cache or publish its checksum manifest if bit-for-bit reconstruction matters.
